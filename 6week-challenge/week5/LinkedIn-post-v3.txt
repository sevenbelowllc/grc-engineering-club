Week 5 of the GRC Engineering Club challenge ("Turn On the Cameras") humbled me — and I'll be honest about why. I learned something about a native AWS service I probably should have understood years ago.

Here's how it went. I stood up AWS Security Hub, enabled the NIST 800-53 standard, and waited for findings to roll in. Nothing came. Every standard just sat there marked INCOMPLETE, all with the same reason: NO_AVAILABLE_CONFIGURATION_RECORDER.

I spent a while confused before it clicked — and when it did, it genuinely changed how I think about the tool.

Security Hub isn't the sensor. It's the reporting layer. For most of its checks it doesn't look at your resources directly; it reads the state that AWS Config has already collected. So no Config recorder means no data, and no data means there's nothing for Security Hub to evaluate. Zero findings.

The part that really got me: Security Hub can't even warn you that Config is off, because it needs Config to produce that finding in the first place. So you end up staring at a clean, green dashboard that actually represents no coverage at all. That's the dangerous kind of "everything looks fine."

Once I added AWS Config through Terraform and gave it about 15 minutes, the findings started flowing. And the first critical one was almost too on-the-nose: Config.1, flagging that my own Config deployment was using a custom IAM role instead of the AWS service-linked role. My own pipeline caught my own mistake — which, honestly, is exactly what I wanted to see.

The real takeaway wasn't about Security Hub at all. It was about GRC.

A control that's enabled isn't the same as a control that's working. Anyone can flip something on; the actual job is confirming it's producing evidence. That's the whole difference between saying you have continuous monitoring and being able to prove it.

"On" is a configuration. "Producing evidence" is a control.
