# OSCAL — the control mapping an assessor can traverse

Two documents. A **profile** that states which controls are in scope, and a
**component definition** that says how each one is implemented and links the
evidence. Both validate clean against OSCAL 1.2.1.

```
catalog (NIST, published)  →  profile  →  component  →  evidence URI  →  verified bundle
```

That chain is the whole point. An assessor who wants to check the SC-28 claim
does not ask for a screenshot or book a call. They read the profile to see
SC-28 is claimed, read the component to see which Terraform resource implements
it and which Rego rule gates it, follow the `rel="evidence"` link to a signed
bundle, and run the linked verifier. The audit becomes a graph traversal.

## The documents

| Path | What it says |
|---|---|
| [`profiles/grc-pipeline-controls/profile.json`](profiles/grc-pipeline-controls/profile.json) | Four control IDs from NIST SP 800-53 Rev 5: `ac-3`, `au-3`, `cm-6`, `sc-28`. Nothing else. |
| [`component-definitions/grc-pipeline/component-definition.json`](component-definitions/grc-pipeline/component-definition.json) | One `implemented-requirement` per control: how it is satisfied, which resource does it, which rule gates it, where the proof lives. |

Both import the published NIST catalog by URL
(`NIST_SP-800-53_rev5_catalog.json`) rather than vendoring a copy. The
authoritative control text stays authoritative.

## What each requirement carries

Every `implemented-requirement` has:

- a **description** in plain language — how the infrastructure satisfies the
  control, and why it is built that way rather than some other way;
- **props** naming the Terraform resource(s), the Rego package that gates it,
  and its `verification-point` (`plan-time` or `runtime`);
- **links** with `rel="reference"` to the exact source lines, pinned to a commit
  SHA so they keep meaning after the branch moves;
- **links** with `rel="evidence"` — two of them (see below);
- a **link** with `rel="verification"` to the script that checks the evidence.

### Why two evidence links

Each control links its bundle twice:

| | |
|---|---|
| `https://raw.githubusercontent.com/…` | A copy **anyone can fetch**, no credentials, no account. Public verifiability. |
| `s3://grc-challenge-evidence-vault-…` | A copy **nobody can delete** — S3 Object Lock in COMPLIANCE mode, undeletable by any principal including the account root until retention expires. |

Either one alone is a weaker claim. A public copy proves the evidence is
reachable but not that it survived; a locked copy proves it survived but is
unreadable to the assessor. Together they cover both.

## The honest part: AU-3 has no policy rule

Three of the four controls are enforced at **plan time**. A pull request that
would remove bucket encryption fails the gate before anything is applied.

AU-3 is not, and its `remarks` field says so at length. A Terraform plan can
show that a CloudTrail trail *will be created*. It cannot show that the trail is
*delivering records*, because delivery is a runtime property of a system that
does not exist yet at plan time. A plan-time rule for AU-3 would produce a green
gate that attests to nothing.

So AU-3's evidence is captured runtime output instead — `get-trail-status`
showing `IsLogging: true` with recent log and digest delivery, plus Security Hub
findings for the same account. That is a **narrower** claim than the plan-time
controls make (true of one moment, not of every future pull request) and a
**stronger** one (about the system, not about the intent).

Writing the gap down is the point. A control mapping that pretends every control
is equally proven is the compliance theatre this pipeline exists to replace.

## Verify it yourself

```bash
pip install compliance-trestle          # 4.2.0, OSCAL 1.2.1
cd 6week-challenge/week-6/oscal

trestle validate -a                     # both documents → VALID
```

Then follow a link and check the evidence it points at:

```bash
# SC-28's evidence link, fetched fresh from the URI in the document
curl -sO https://raw.githubusercontent.com/sevenbelowllc/grc-engineering-club/1d97be7f0763223db7a42b805375c6302fd24e14/6week-challenge/week-4/evidence/evidence.tar.gz

cd ../../week-4 && ./verify-evidence.sh evidence/evidence.tar.gz
# integrity:    OK
# authenticity: OK
# CHAIN INTACT
```

[`../../../traverse.sh`](../../../traverse.sh) does the whole walk automatically —
profile → component → evidence href → fetch → verify.

## Authoring

The documents are generated by
[`authoring/generate-documents.py`](authoring/generate-documents.py), not typed
by hand. Two reasons:

1. **UUIDs must be generated v4.** OSCAL rejects anything else, and
   hand-writing them is the most common way a trestle document fails validation.
2. **One source of truth.** The commit pin, the namespace, and the evidence URIs
   appear in a dozen places across four requirements. Deriving them from
   constants means a link cannot be correct in three places and stale in the
   fourth.

The script is **one-shot**: re-running it mints fresh UUIDs and a fresh
`last-modified`, producing semantically identical documents that no longer match
their signatures. The committed JSON is authoritative. Regenerate only when
changing content, and re-sign afterwards.

## Namespaces

Props that OSCAL defines use the NIST namespace (`implementation-status` under
`http://csrc.nist.gov/ns/oscal`). Props specific to this pipeline
(`terraform-resource`, `policy-package`, `verification-point`) use
`https://sevenbelow.com/ns/oscal`. Inventing a name inside the NIST namespace
would be claiming NIST defined it.

## Directory layout

`trestle init` creates the full OSCAL model tree — `catalogs/`,
`system-security-plans/` and the rest — most of which is empty here. The empty
directories are kept rather than pruned so the workspace stays a valid trestle
project that `trestle validate -a` and `trestle assemble` can operate on without
reinitialising. (`dist/` is trestle's build output and is gitignored; `trestle
assemble` recreates it.)

Populated: `component-definitions/`, `profiles/`, and `assessment-results/`
(see [`../assessment-results.md`](../assessment-results.md)).
