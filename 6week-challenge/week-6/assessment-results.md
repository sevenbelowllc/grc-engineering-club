# From policy verdicts to assessment results

The week-6 brief asks for two OSCAL documents: a profile and a component
definition. Those say what is claimed and how it is implemented. They do not say
whether it is *currently true*.

That gap is where compliance work usually goes to die. The pipeline already
knows the answer — `conftest` prints it on every pull request — but the answer
lives in a JSON file shaped like this:

```json
{ "namespace": "compliance.sc28_aws", "successes": 1 }
```

and an assessor needs it shaped like this:

```json
{ "target": { "type": "objective-id", "target-id": "sc-28_obj",
              "status": { "state": "satisfied" } } }
```

Somebody has to carry it across. If that somebody is a person, they do it again
every time the gate runs, and the moment they stop, the mapping goes stale
without anyone noticing. [`oscal-from-conftest.py`](oscal-from-conftest.py) does
it mechanically.

## What it produces

```
conftest --output json  →  oscal-from-conftest.py  →  OSCAL assessment-results
```

One **observation** per policy package — what was evaluated, against which file,
with the denial messages verbatim from the policy engine. One **finding** per
control — satisfied or not-satisfied, pointing back at the exact
`implemented-requirement` in the component definition by UUID.

| Document | Source | Result |
|---|---|---|
| [`grc-gate-run/`](oscal/assessment-results/grc-gate-run/assessment-results.json) | The CI-signed week-4 bundle's conftest verdicts | 3 findings, all satisfied |
| [`broken-plan-negative-control/`](oscal/assessment-results/broken-plan-negative-control/assessment-results.json) | `week-3/plan-broken.json` | 3 findings, **SC-28 not-satisfied** |

The second one matters as much as the first. A pipeline that has only ever
emitted passing results has not been shown to be *capable* of emitting a failing
one — that is the difference between a control and a decoration. The negative
control is generated by the same script from a plan with the encryption
resources removed, and it is labelled as a negative control in its own metadata
so nobody mistakes it for a production verdict.

## The design decision that matters

**The control mapping is not in the converter.**

There is no dictionary in `oscal-from-conftest.py` saying `compliance.sc28_aws`
means `sc-28`. That mapping lives in the component definition, as a
`policy-package` prop on each `implemented-requirement`, because the component
definition is the document whose job is to say how a control is implemented. The
converter reads it back out at conversion time.

```python
# read_control_mapping() — the entire mapping logic
packages = [p["value"] for p in req.get("props", [])
            if p.get("name") == "policy-package"]
```

The consequences are the whole point:

- Add a control to the component definition with a `policy-package` prop, and
  its verdicts start converting. No change here.
- Rename a Rego package without updating the component definition, and the
  converter **refuses to run** rather than silently dropping a control.
- The converter cannot claim a control the component definition does not
  implement, because it has no independent source for the list.

A converter with a hardcoded table is a third place the truth lives, and the
third place is always the one that goes stale.

## It fails loudly in both directions

Two symmetric guards, both exiting `3` with no output written:

**An unmapped namespace** — conftest tested something the component definition
never claimed. A control is being gated and the assurance is going nowhere:

```
mapping error: conftest reported on package 'compliance.ia5_secrets', which no
implemented-requirement in the component definition claims via a
'policy-package' prop.
  Known packages: compliance.ac3_aws, compliance.cm6_aws, compliance.sc28_aws
  Fix the component definition, not this script — the mapping is supposed to
  live there.
```

**A missing verdict** — the component definition claims a rule gates a control,
but the gate returned nothing for it:

```
mapping error: the component definition claims these policy packages gate a
control, but conftest reported no result for them:
  compliance.sc28_aws  (control sc-28)
An absent verdict is not a passing verdict. Either the gate did not run the
policy, or the component definition is claiming a rule that no longer exists.
```

The second is the one that would otherwise bite. A policy file that silently
stops loading produces conftest output with one fewer entry and a zero exit
code. Without this check, the pipeline would keep emitting a valid-looking
assessment-results document that simply no longer mentions SC-28, and a green
build would mean less every month without anything turning red.

Transcript of all three cases: [`evidence/converter-guards.txt`](evidence/converter-guards.txt).

## Reproducible output

Running the converter twice on the same input produces **byte-identical** JSON.

That is harder than it sounds, because OSCAL requires a v4 UUID on nearly every
object — the datatype regex literally pins the version nibble to `4`, which
rules out `uuid5`, the obvious tool for deriving an identifier from a name. So
the UUIDs here are derived by SHA-256 over a stable key, with the version and
variant bits then set to what a v4 UUID carries. They are hash-derived
identifiers wearing v4's syntax, and the docstring in the script says so plainly
rather than letting a reader assume randomness.

The payoff is that a reviewer can regenerate the committed document and `diff`
it. If the bytes match, the document is exactly what the verdicts say it is.
A converter that emitted fresh random UUIDs would make that check impossible —
every regeneration would differ, and no reviewer could tell a changed verdict
from a changed random number.

The assessment timestamp is an input rather than `now()` for the same reason,
and it is not asserted by hand. The `grc-gate-run` document is stamped
`2026-07-22T01:16:40+00:00`, which is the `integratedTime` of the Rekor
transparency-log entry for the signature over that evidence bundle:

```bash
python3 -c 'import json,datetime;b=json.load(open("../week-4/evidence/evidence.tar.gz.sig.bundle"));
e=b["verificationMaterial"]["tlogEntries"][0];
print(datetime.datetime.fromtimestamp(int(e["integratedTime"]),datetime.timezone.utc))'
# 2026-07-22 01:16:40+00:00
```

The "when" of the assessment comes from a public append-only log run by someone
else, not from the author's clock.

## Why there is also an assessment plan

OSCAL makes `import-ap` a **required** field on `assessment-results` — results
are, by construction, the answer to a plan. So the converter needs a plan to
point at, and [`assessment-plan.json`](oscal/assessment-plans/grc-pipeline-assessment/assessment-plan.json)
is it.

It turned out to be the right place to state the method split. The plan has two
`control-selections`: three controls assessed by automated policy evaluation
before apply, and AU-3 assessed by examining captured runtime output. That split
is the assurance boundary of the whole pipeline, and putting it in the model
means an assessor reads it rather than taking it on trust from a README.

The plan's own `import-ssp` field is the one place the model does not fit. OSCAL
expects an assessment plan to target a System Security Plan; this build has no
SSP, because the thing being assessed is a reusable pipeline component, not an
authorization boundary with a system owner and a FIPS-199 categorisation.
Inventing a thin SSP to fill the field would be worse than saying so, so
`import-ssp` resolves to a back-matter resource for the component definition and
a `remarks` field states in full what is and is not being claimed.

## Run it

```bash
cd 6week-challenge/week-6

./oscal-from-conftest.py \
  --conftest    ../week-3/evidence/conftest-results.json \
  --component   oscal/component-definitions/grc-pipeline/component-definition.json \
  --plan-href   ../../assessment-plans/grc-pipeline-assessment/assessment-plan.json \
  --evidence    https://raw.githubusercontent.com/sevenbelowllc/grc-engineering-club/1d97be7f0763223db7a42b805375c6302fd24e14/6week-challenge/week-4/evidence/evidence.tar.gz \
  --evidence    s3://grc-challenge-evidence-vault-f11fcaca/manual/2026-07-26/evidence.tar.gz \
  --assessed-at 2026-07-22T01:16:40+00:00 \
  -o oscal/assessment-results/grc-gate-run/assessment-results.json

cd oscal && trestle validate -a
```

Standard library only — no dependencies beyond Python 3.9+.
